# ADR 0010 기록과 장비 통합 계약

- 상태는 승인이다. 사용자가 S10 실행 계획을 승인하고 구현을 요청했다.
- 날짜는 2026-11-20이다.
- 관련 단계는 [S10](../steps/S10-record-device-integration.md)이다.
- 관련 요구사항은 F05, F06, F07, F08, F10이다.
- 구현 검증은 [S10 단계 기록](../steps/S10-record-device-integration.md)을 따른다.

## 문제와 제약

파일과 TCP가 같은 검사·저장 경로를 사용한다. 저장이나 전송이 실패해도 검사 판정이 유지되어야 한다. 운영 모드에서는 DB 준비가 확인된 뒤 새 검사를 수락한다. [S05 저장 제안](0005-inspection-history.md), [S06 TCP 계약](0006-virtual-device-protocol.md), [S09 작업 수명](0009-mfc-file-inspection.md)이 출발점이다.

## 대안과 선택

| 대안 | 영향 |
|---|---|
| **x64 단일 MFC 프로세스** | 기존 x64 MySQL C 클라이언트와 저장 어댑터를 직접 사용한다. x64 MFC 설치와 OpenCV 재빌드가 필요하다. |
| ARM64 MFC와 ARM64 MySQL 클라이언트 | 기존 ARM64 앱과 OpenCV를 사용한다. 같은 저장 계약을 지원하는 ARM64 클라이언트의 빌드, 연결, 장애 복구 검증이 필요하다. |
| ARM64 MFC와 x64 저장 보조 프로세스 | 검증된 두 아키텍처를 활용한다. 프로세스 간 전달, 종료, 보조 프로세스 장애 복구 계약이 추가된다. |

첫 번째 안을 적용한다. 기존 MFC·OpenCV·MySQL API를 사용하고 파일과 TCP 요청을 하나의 프로세스 안에서 조정한다. Windows ARM VM의 기존 ARM64 빌드는 S09 파일 검사의 회귀 검증에 사용한다.

## 작업과 저장

- 실행 슬롯은 분석과 저장을 포함해 1개이며 대기 슬롯은 0개다. 결과·저장 상태와 요청 식별자는 조정 경계가 소유한다. 잠금은 상태 전이에만 쓰고 이미지 계산, DB·네트워크 호출은 잠금과 UI 스레드 밖에서 수행한다.
- 시작 시 운영 계정으로 연결과 이력 테이블 접근을 확인한다. 새 작업의 저장 실패나 커밋 응답 유실이 발생하면 새 입력 수락을 중단한다. 현재 작업의 저장 레코드와 ID를 메모리에 두고, MFC의 저장 재시도 또는 같은 TCP 요청으로 저장만 재시도한다. 저장 성공 또는 동일 레코드의 재전송 확인 뒤 입력을 다시 연다. 후속 재시도가 실패해도 커밋 여부가 확인될 때까지 저장 확인 필요 상태를 유지한다.
- 파일 요청 ID는 `file-`과 Windows가 생성한 GUID로 만든다. TCP에서는 해당 접두사를 예약한다. 검사 ID도 GUID로 생성해 요청 ID와 함께 최초 저장부터 유지한다. 저장된 TCP 요청은 MySQL의 `request_id` 고유키로 찾는다. 등록된 입력·설정 ID는 각각 고정 바이트의 SHA-256과 연결한다. 장비 작업은 시작 시 확인한 설정을 사용하고 취소나 입력 오류 행에도 그 설정 해시를 기록한다. 저장된 요청의 입력 ID와 설정 해시를 확인한 뒤 기존 응답을 복원한다. 바이트를 바꿀 때는 새 등록 ID를 사용한다. 조회와 작업 완료가 교차해도 같은 요청을 새 작업으로 수락하지 않도록 조회 결과를 슬롯 상태와 함께 재확인한다.
- 취소는 공용 분석이 최종 결과를 넘기기 전까지 수락한다. 수락한 취소는 작업 상태 `CANCELLED`, NULL 판정, 시도 0건으로 저장한다. 완료 상태 `COMPLETED`는 `PASS`, `FAIL`, `REVIEW`, `ERROR` 중 하나를 가진다. 원본·설정 해시는 실제 바이트가 확보된 때 기록한다. 마이그레이션은 기존 행을 `COMPLETED`로 읽고 검사·요청 ID와 기존 판정을 보존한다.
- 종료 시 입력 수락을 닫고 진행 중 작업에 정지 요청을 보낸 뒤 작업과 TCP 리스너를 회수한다. 이미 시작한 MySQL 호출을 회수할 때는 연결·조회 제한 시간까지 대기할 수 있다. 미저장 작업이 남으면 사용자에게 표시한다. 프로세스 수명 안에서 저장을 재시도할 수 있다.

## TCP 계약

S06의 `127.0.0.1` 바인딩, `INSPECT` 요청, TAB과 LF, 본문 256바이트, 수신·송신 마감을 사용한다. 한 연결에서 순서대로 프레임을 처리한다. 가상 장비는 같은 `INSPECT`를 재전송해 상태를 조회한다. `RESULT`의 판정은 저장된 값이다. `<TAB>`과 `<LF>`는 실제 구분 문자다.

저장된 요청 조회는 리스너 밖에서 한 건씩 실행한다. 리스너는 조회를 최대 150ms 기다린다. 결과가 아직 없으면 `BUSY`로 재전송을 안내한다. 현재 처리 중인 같은 요청은 메모리에 있는 상태로 즉시 응답한다.

| 조건 | 응답 |
|---|---|
| 새 요청 수락 또는 같은 요청 처리 중 | `STATUS<TAB>request_id<TAB>inspection_id<TAB>IN_PROGRESS<LF>` |
| 저장 확정 또는 저장된 요청 재전송 | `RESULT<TAB>request_id<TAB>inspection_id<TAB>decision<LF>` |
| 취소 이력 저장 확정 | 같은 `STATUS` 형식으로 `CANCELLED` |
| 미저장 또는 커밋 응답 유실 | 같은 `STATUS` 형식으로 `UNSAVED` 또는 `COMMIT_UNKNOWN`을 반환하고 저장 재시도를 시작한다. 재시도 중 같은 요청에는 `IN_PROGRESS` |
| 실행 슬롯 점유 중 새 요청 또는 저장된 요청 조회 대기 | `ERROR<TAB>request_id<TAB>BUSY<LF>` |
| DB 미준비 또는 미저장 작업 존재 시 새 요청 | 같은 `ERROR` 형식으로 `DB_UNAVAILABLE` |
| 같은 ID에 다른 입력이나 설정 | 같은 `ERROR` 형식으로 `REQUEST_CONFLICT`. 중복 비교는 새 작업의 슬롯·등록 검증보다 먼저 수행 |
| 예약된 파일 요청 ID, 미등록 또는 잘못된 프레임 | `RESERVED_REQUEST_ID`, 기존 `UNKNOWN_SOURCE`·`UNKNOWN_CONFIG` 또는 `BAD_FRAME` |
| 등록 설정의 바이트 검증 실패 | `CONFIG_UNAVAILABLE`. 새 장비 입력을 수락하지 않는다 |

## 검증과 재검토

[S10 실행 계획](../steps/S10-record-device-integration.md)의 실제 통합 검수로 DB 단절, 커밋 응답 유실, 재연결·재시작 동일성, 포화와 취소를 확인한다. x64 실행 조건, 두 개 이상의 동시 분석 요구 또는 재시작 뒤 미저장 작업 복구 요구가 생기면 해당 계약을 다시 검토한다.
